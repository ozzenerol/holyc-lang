Known issues

Bugs found while writing and testing these docs and while testing the compiler, each with a way to reproduce it and a workaround. The other pages avoid them, so every example there works as shown.

Compiler

ProblemReproduceWorkaround
A definition drops the default arguments of its prototype I64 F(I64 *v, I64 n=2); then I64 F(I64 *v, I64 n) { ... }: F(a) fails with "Unexpected number of arguments 1 in call to F(), expected 2 args" Repeat the default in the definition
A function pointer can't be called as (*fp)() U0 (*fp)() = &G; (*fp)(); is an error ("The `*` operator cannot be applied to a function pointer"); C accepts it Call it as fp()
The C transpiler gets array members wrong With class Leaf { I64 a, b; };, Leaf leaves[2]; is written as Leaf leaves[32]; (bytes, not elements), and b.leaves[1].a as *(b.leaves[1]).a, which doesn't compile The transpiler is experimental; fix the C output by hand
Cross-compiling to macOS from Linux fails to assemble --target=*-apple-darwin on Linux still emits .section .note.GNU-stack, which the Mach-O assembler rejects Build on the Mac

Diagnostics

ProblemReproduceWorkaround
A wrong argument type is reported at the closing parenthesis Take(y); with a class-typed parameter warns at the ), not at y Check every argument of the call
A class initialiser warning lands one item late class Q { I64 a; I64 *p; }; F64 f; Q qq = {1, f}; warns at the } after f Look at the item before the caret
Some type errors are reported twice I64 y = 1; P p; y = p; prints a warning and an error for the same statement Read the error and ignore the warning
The underline under a string token leaves out its quotes I64 s = 2 "abcd" 3; underlines 4 characters from the opening quote None needed
The warning for a value returned from a U0 function misprints the expression return g++; is shown as ++g; return Twice(Twice(1)); as Twice(Twice(1);); Read the line number in the warning
A missing name after a comma is reported on the next line I64 a, ; reports "Identifier expected: got TK_PUNCT ;" with the caret on the start of the following line Look at the end of the previous line

JIT and code generation

ProblemReproduceWorkaround
The legacy x86 backend has several wrong-code bugs Only with --use-legacy-x86: F64 R(I64 n) { return n; } returns 0.0; narrow loads read 8 bytes (I32 a[3] = {1,2,3}; a[0] is 8589934593); some global class initialisers panic with "Global variables unimplemented"; the exit status of U0 Main is garbage Use the default backend
A class-typed item in a local initialiser list is garbage With class L { I64 a; P p; I64 b; };, a local L l = {1, p0, 4}; leaves l.p holding pointer-like garbage; so does a local P ps[2] = {p0, p0};. The same initialisers on globals work Assign the class fields after the declaration (l.p = p0;), or make the variable global

Standard library

ProblemReproduceWorkaround
NetSetSocketNoDelay returns the opposite of what happened It returns FALSE when setsockopt succeeds Ignore its result, or call setsockopt yourself
ThreadPoolRelease hangs After ThreadPoolWait, ThreadPoolRelease never returns: the workers are never woken before pthread_cond_destroy, and detached threads are joined Don't release the pool; let the process exit
JsonParse ignores its flags argument JsonParse(text, -1, JSON_STRNUM_FLAG) behaves like flags 0 None
RBTreeRelease leaks It frees the nodes but not the tree itself, and never calls the key/value free functions Free keys and values yourself before releasing

Reporting

Please report bugs on GitHub. A minimal .HC file that reproduces the problem helps the most.
